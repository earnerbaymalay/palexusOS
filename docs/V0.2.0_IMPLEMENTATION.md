## Module 1: ThemeManager

### Purpose
Support multiple design themes (light/dark, brand variants, accessibility modes) without token duplication.

### Design

```
ThemeManager
├── Load multiple token sets
├── Merge with conflict resolution
├── Export theme-specific variables
└── Support runtime theme switching

API:
  manager = ThemeManager()
  manager.add_theme("dark-mode", tokens_file)
  manager.add_theme("high-contrast", tokens_file)
  
  css = manager.export_theme("dark-mode", format="css")
  manager.switch_theme("high-contrast", active_user)
```

### Specification

**File**: `palexus/design/theme_manager.py`

**Core Classes**:
```python
class Theme:
    """Represents a single theme."""
    name: str
    tokens: Dict[str, Any]
    priority: int  # For conflict resolution
    
class ThemeManager:
    """Manage multiple themes."""
    
    def __init__(self):
        self.themes: Dict[str, Theme] = {}
        self.current_theme: Optional[str] = None
    
    def add_theme(self, name: str, tokens: Dict) -> None:
        """Add a theme."""
    
    def merge_themes(self, theme_names: List[str]) -> Dict:
        """Merge themes with priority-based resolution."""
    
    def export_theme(self, name: str, format: str = "css") -> str:
        """Export theme in specified format."""
    
    def switch_theme(self, name: str, user_id: Optional[str] = None) -> None:
        """Switch active theme."""
    
    def get_theme_tokens(self, name: str) -> Dict:
        """Get tokens for theme."""
```

**Tests** (20+ test cases):
- Single theme load
- Theme merging (2, 3, 5 themes)
- Conflict resolution (priority order)
- Export formats (CSS, JSON, JavaScript)
- Runtime switching
- User-specific themes
- Fallback chains

**Integration**:
- Used by DesktopEnvironment for theme management
- Integrates with TokenRegistry for token resolution
- Provides hooks for theme change callbacks

**Timeline**: 2 weeks

## Module 2: VariableRegistry

### Purpose
Central registry for environment variables and secrets, with secure credential management.

### Design

```
VariableRegistry
├── Load environment configuration
├── Manage secrets securely (not in Git)
├── Support build-time and runtime injection
└── Integration with DesktopEnvironment

API:
  registry = VariableRegistry()
  registry.load_from_env()
  registry.set_secret("db_password", "***")

  value = registry.get("API_KEY", default="")
  expanded = registry.expand(
    "connection_string="
    "${DB_HOST}:${DB_PORT}")
```

### Specification

**File**: `palexus/core/variable_registry.py`

**Core Classes**:
```python
class Variable:
    """Environment variable."""
    name: str
    value: str
    scope: Enum  # BUILD, RUNTIME, BOTH
    encrypted: bool
    
class VariableRegistry:
    """Manage environment variables and secrets."""
    
    def __init__(self):
        self.variables: Dict[str, Variable] = {}
    
    def load_from_env(self, prefix: str = "PALEXUS") -> None:
        """Load variables from environment."""
    
    def load_from_file(self, file_path: Path) -> None:
        """Load from .env file (dev only)."""
    
    def set_secret(self, name: str, value: str) -> None:
        """Set a secret (never logged, encrypted at rest)."""
    
    def get(self, name: str, default: str = "") -> str:
        """Get variable value."""
    
    def expand(self, template: str) -> str:
        """Expand template with variable values."""
    
    def validate(self) -> bool:
        """Verify all required variables are set."""
```

**Tests** (15+ test cases):
- Environment variable loading
- Secret encryption/decryption
- Variable expansion (simple, nested, missing)
- Validation (required vs optional)
- Scope isolation (build vs runtime)
- File-based loading (.env)
- Circular reference detection

**Integration**:
- Build-time injection in CLI
- Runtime injection in modules
- Security: never log secrets, encrypt at rest

**Timeline**: 2 weeks

## Enhancement 1: TokenRegistry - Token Inheritance

### Purpose
Semantic tokens reference primitives, reducing duplication.

### Design

```
Primitive Layer:
  blue/500: "#0066FF"

Semantic Layer (with references):
  color/bg/primary: {"ref": "blue/500"}
  color/text/secondary: {"ref": "blue/700"}

When blue/500 changes → all dependents update automatically
```

### Specification

**Changes to**: `palexus/design/token_registry.py`

**New Methods**:
```python
def resolve_references(self) -> Dict:
    """Resolve all token references."""

def get_token_with_inheritance(self, path: str) -> str:
    """Get token value, following references."""

def detect_circular_references(self) -> List[str]:
    """Detect circular reference chains."""

def trace_inheritance(self, token_path: str) -> List[str]:
    """Show full inheritance chain."""
```

**Tests** (20+ test cases):
- Simple references (1 level)
- Chain references (2+ levels)
- Circular reference detection
- Missing reference handling
- Export with resolved values
- Performance (resolve 1000+ tokens)

**Timeline**: 1.5 weeks

## Enhancement 3: GateRegistry - Plugins System

### Purpose
Enable third-party gates without modifying core code.

### Design

```
Plugin Architecture:
  palexus.build.gates (core gates)
  palexus_plugins.custom_gates (third-party)
  
Plugin Discovery:
  - Load from entry points
  - Load from plugin directory
  - Register with GateRegistry
```

### Specification

**Plugin Interface**:
```python
class GatePlugin:
    """Base class for gate plugins."""
    
    def name(self) -> str:
        """Gate name."""
    
    def dependencies(self) -> List[str]:
        """Gate dependencies."""
    
    def verify(self, repo_root: Path) -> Dict:
        """Run verification."""
        return {
            "passed": bool,
            "error": Optional[str]
        }

# Registration:
@gate_plugin(name="custom-lint", depends_on=["package"])
def verify_custom_lint(repo_root: Path) -> Dict:
    # Verification logic
    return {"passed": True}
```

**Tests** (10+ test cases):
- Plugin loading (entry points, directory)
- Dependency resolution with plugins
- Plugin execution
- Error handling
- Plugin composition

**Timeline**: 1 week

## Tooling 1: `palexus` command (extend the existing CLI)

### Current state (shipped on `main`)

`palexus` is installed as a console script and dispatches to the per-module
CLIs. Each is a thin argparse layer over its module, with tests in
`tests/test_cli.py`:

```bash
palexus design list | validate | \
  export {css,shell,kitty,xfce} OUT
palexus build  list | run [--gates a,b] | status
palexus test   list | run ...
palexus --version
```

`palexus-design`, `palexus-build` and `palexus-test` remain as aliases.

### v0.2.0 work

- `palexus design theme list/export NAME`
  - Backed by: ThemeManager
  - Notes: New subcommands on `palexus/design/cli.py`
- `palexus design export json`
  - Backed by: TokenRegistry
  - Notes: Add a `JSONExporter` beside the existing four
- `palexus vars check`
  - Backed by: VariableRegistry
  - Notes: New `palexus/core/cli.py`, registered in `palexus/cli.py` `COMMANDS`
- `palexus test run` that runs something
  - Backed by: TestOrchestrator
  - Notes: Today no suites are registered, so `run` executes nothing; register pytest-backed suites first

Rule for every new command: the module does the work; the CLI parses
arguments, calls one method, formats the result, returns an exit code. Each
command gets a test that calls `main([...])` directly.

**Timeline**: 1 week (the scaffolding exists).
